# 記録保存と集計の更新

## 反映順序

1. Supabaseのmigration適用履歴を確認し，既存migrationが適用済みであることを確認する．
2. `supabase/migrations/20260925060000_atomic_workout_save.sql` を適用する．
3. 開発・検証DBで `supabase/verification/workout_save.sql` を実行する．
4. アプリをデプロイする．
5. iPhoneで新規記録，編集，再読み込み，左右別回数，下書き復元，集計ページの期間切替を確認する．

新しいアプリは `save_workout` RPCを必要とする．
DB更新前にアプリを配信すると保存が失敗するため，DBを先に更新する．
RPCがない場合に従来の複数リクエストへ戻す処理は設けない．
既存の記録やテーブルの削除は行わない．
このmigrationの追加は，旧アプリの読み書きとは共存可能である．

### Supabase Dashboardから適用する場合

1. 対象ProjectのSQL Editorで「New query」を開く．
2. `supabase/migrations/20260925060000_atomic_workout_save.sql` の全文を貼り付ける．
3. 「Run」を押し，エラーがないことを確認する．
4. 次のSQLで関数の存在を確認する．

```sql
select to_regprocedure('public.save_workout(uuid,uuid,date,uuid,text,text,integer,jsonb)');
```

結果がNULLでなければ関数が存在する．
SQL Editorによる手動実行はCLIのmigration履歴を自動更新しない．
Supabase CLIを使っている場合は，対象Projectへのlinkを確認し，適用済みのSQLと一致することを確認してから `supabase migration repair 20260925060000 --status applied --linked` で履歴を合わせる．
同じ `create function` を再実行すると既存関数のエラーになるため，重複実行しない．

Supabase CLIで管理している環境では，通常は `supabase migration list` で差分を確認し，`supabase db push` による適用を優先する．
[Supabase公式のmigration手順](https://supabase.com/docs/guides/deployment/database-migrations)も参照できる．

## 保存の保証

Workout，Workout内種目，セットの保存は単一のPostgreSQL関数内で実行する．
セットの制約違反などで失敗すると，親行の変更と旧セットの削除もロールバックされる．
編集時は親Workoutをロックし，親子IDの対応と所有者を確認する．
関数はsecurity invokerであり，authenticatedのGRANTとRLSを適用する．
他ユーザーの行へのアクセスは拒否する．

同時編集は順番に保存され，最後の保存が優先される．
通信応答だけが失われた新規作成の再送を完全に重複排除する仕組みは，今回の変更には含まない．

## 期間と計算定義

ホームの「集計を表示」から `/stats` に移動し，1週間・1か月・1年・全期間を切り替える．
初期選択は1か月で，履歴一覧の範囲は変更しない．
端末の今日を終端とし，1週間は今日を含む7日間とする．
1か月・1年は暦でさかのぼった日の翌日から今日までとし，存在しない日は月末へ補正する．
例：2026年9月25日の1か月は8月26日～9月25日となる．
選択中の開始日と終了日を画面に表示する．
週平均は期間内の実施日数を期間の週数で割り，消費カロリーは実施日当たりの平均とする．

最大量は1セットの重量×回数の最大値であり，セッション全セットの合計ではない．
左右別種目は片側の重量×（左回数＋右回数）を使用する．
推定1RMは左右の多い側の回数を使い，共通関数で計算した後に表示時だけ小数第1位へ丸める．

## 再発防止

- 全件取得は `lib/supabase/read-all.ts` を通し，一意なIDまで含む安定した順序でページを取得する．
- 親IDリストは100件ずつに分割し，URL長と取得件数の上限を抑える．
- PGliteで実際のmigrationを適用し，保存失敗時の復元とユーザー間の分離を自動テストする．
- 1,000件超の集計，期間境界，左右別回数，共通1RM関数との一致をテストする．
- GitHub Actionsでlint，型検査，テスト，ビルドを実行する．
- `AGENTS.md` と `AGENT.md` をGit管理し，作業方針を共有する．

PGliteテストのAuth部分は最小限の模擬実装であり，SupabaseのOAuthや実際のData APIは対象外である．
本番へのmigration適用とiPhone実機確認は別途必要である．
